CHADREY WHOLESALE — SUPABASE AND FLUTTERWAVE SETUP GUIDE

Status

This guide applies to the current Chadrey Wholesale milestone. Stripe is intentionally deferred. The current payment integration supports Flutterwave hosted-checkout initiation and a server-side webhook boundary that validates the webhook hash, verifies the transaction with Flutterwave, checks invoice reference/currency/amount, prevents duplicate transaction processing, persists the payment, updates the invoice/order workflow, and sends the owner alert for a verified payment.

Required server secrets

Store these values in the secure server-side secret store connected to the application. If Supabase is your secret-management source, add them to the Supabase project’s server/deployment secrets and map them into the deployed application environment. Do not commit them to GitHub and do not expose them through client-side code or VITE_ variables.

FLUTTERWAVE_SECRET_KEY
Use the Flutterwave Secret Key from the Flutterwave Dashboard. This is used only by the server to create hosted checkout links and to verify transactions through Flutterwave’s API. Use a test key in sandbox mode and a live key only in production.

FLUTTERWAVE_WEBHOOK_HASH
Use the webhook secret/hash configured in Flutterwave. The server compares this value with the incoming verif-hash header before reading the payment event.

Webhook URL

Configure Flutterwave to send webhook events to:

https://YOUR-PUBLISHED-CHADREY-DOMAIN/api/webhooks/flutterwave

The webhook must be HTTPS in the deployed environment. Use a secure public HTTPS tunnel only for local testing.

Payment reference format

The application uses invoice-N as the Flutterwave transaction reference, where N is the internal invoice ID. For example, invoice-42 refers to invoice ID 42. A webhook with no invoice reference is ignored, and an unknown invoice is rejected.

Verification sequence

The server first validates verif-hash. It then extracts the transaction ID and invoice reference, checks for a previously persisted transaction, loads the invoice, calls Flutterwave’s transaction verification endpoint, confirms the transaction reference, currency, and amount, persists a successful Flutterwave payment, creates or reuses the processing order, updates payment/order status, and sends the owner notification. Replayed webhook deliveries must not create duplicate payment records or duplicate orders.

Customer and admin routes

The public catalogue is available at /products. Product detail pages are available at /product?id=PRODUCT_ID. Customers create requests at /quote and review persisted requests at /dashboard. Quotation review is available at /quotation?quoteId=QUOTE_REQUEST_ID. Quote conversations are available at /messages?quoteId=QUOTE_REQUEST_ID. Customer order tracking is available at /orders?orderId=ORDER_ID. Administrators use /admin, compose quotations at /admin/quote?quoteId=QUOTE_REQUEST_ID, and manage fulfilment at /admin/fulfilment.

Testing checklist

Use Flutterwave test mode first. Create an accepted quotation and invoice, initiate hosted checkout, complete a sandbox transaction, and confirm that the webhook reaches the published application. Verify that an invalid verif-hash returns HTTP 401. Verify that a successful event creates one payment record and one processing order. Replay the same event and verify that it is treated as a duplicate. Confirm that the customer receives in-app notifications for quote received, quotation sent, invoice issued, and order shipped. Confirm that the owner alert is sent for a new quote and a verified payment only.

Security requirements

Keep both secrets server-only. Never place them in React source, HTML, browser storage, GitHub, or VITE_ variables. Rotate the values if exposed. Keep Flutterwave test and live environments separate. Do not treat a browser redirect as payment proof; server-side transaction verification is authoritative.

Stripe status

Stripe remains deferred. No Stripe secret, publishable key, webhook signing secret, or Stripe checkout route is required for this milestone. Stripe can be added later as a parallel provider after Stripe credentials are configured in the project settings.
